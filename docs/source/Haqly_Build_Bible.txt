PART 1 — WHAT HAQLY IS
(extracted from web app — this is the product foundation)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Haqly is a personal finance app for the Ethiopian market.
Currency is ETB — Ethiopian Birr, formatted as "Br 1,250.00".
The product thesis: not just what did you spend, but was it worth it.

Six features. Nothing else.

  1. EXPENSE TRACKING
     Log name + amount + category.
     Tracked across: today / this week / this month.
     Compared against an optional budget.
     Categories: Meals, Transport, Extras, Bills, Health, Other.
     User can add/remove custom categories.

  2. VALUE CHECK (The "Check" feature)
     Pre-purchase calculator.
     Formula: cost per use = price ÷ number of uses.
     Output: verdict (worth / maybe / not) + regret score (1–5).
     Thresholds:
       Under Br 1 per use  → worth  → regret 1–2
       Br 1–5 per use      → maybe  → regret 3
       Over Br 5 per use   → not    → regret 4–5
     Every check is saved to history.

  3. VALUE SCORE
     Aggregate score across all saved checks.
     Formula: score = ((worth_count × 100) + (maybe_count × 50)) / total
     Range: 0–100.
     Labels:
       75–100 → Smart spender
       50–74  → On track
       25–49  → Needs attention
       0–24   → Review spending

  4. LEDGER
     Tracks money lent and borrowed.
     Supports ETB and USD.
     Fields: person, amount, currency, type (lent/borrowed), note, settled.
     Links to contacts.
     Includes a bill-splitting calculator.
     Open unsettled entries surface on the home screen.

  5. HISTORY
     Full timeline of expenses.
     Grouped by date with day labels (Today, Yesterday, then date).
     Filterable by category.
     Weekly bar chart showing 7-day spend pattern.
     Edit and delete inline.

  6. INSIGHTS
     Rule-based text insight generated from expenses + verdicts.
     Logic priority (from lib/utils.ts — generateInsight()):
       If 50%+ of verdicts are "not"     → warn about purchase quality
       If 80%+ of verdicts are "worth"   → reinforce smart spending
       If one category > 50% of spend    → surface the dominant category
       If nothing logged today           → nudge to log
       If 10+ expenses total             → "patterns are emerging"
       Default                           → consistency nudge

BUSINESS LOGIC RULES — EXACT (from web app lib/utils.ts)
----------------------------------------------------------
These are not approximations. These are the exact rules in production.

  br(n)
    Formats as "Br " + toLocaleString('en', { minimumFractionDigits: 2 })
    Handles string input via parseFloat.
    Returns "Br 0.00" for non-finite values.

  calcCheck(price, uses)
    costPerUse = price / uses
    verdict:
      costPerUse < 1    → 'worth'
      costPerUse <= 5   → 'maybe'
      costPerUse > 5    → 'not'
    regret:
      costPerUse < 1    → 1
      costPerUse <= 3   → 2
      costPerUse <= 5   → 3
      costPerUse <= 10  → 4
      costPerUse > 10   → 5

  calcValueScore(verdicts[])
    worthPct = round((worth_count / total) * 100)
    maybePct = round((maybe_count / total) * 100)
    notPct   = round((not_count   / total) * 100)
    score    = round(((worth_count * 100) + (maybe_count * 50)) / total)

  greeting()
    hour < 12   → 'Good morning'
    hour < 18   → 'Good afternoon'
    else        → 'Good evening'

  dayLabel(iso)
    Compares in local timezone (not UTC).
    Today     → 'Today'
    Yesterday → 'Yesterday'
    Else      → toLocaleDateString('en', { weekday:'long', month:'short', day:'numeric' })

PART 4 — DATA FLOW (the rule that drives everything)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ONE RULE: screens never touch Supabase directly.

  WRITE PATH
    Screen calls Repository.save(data)
        ↓
    Repository writes to SQLite (immediate)
        ↓
    Repository calls queueWrite(table, id, 'insert', payload)
        ↓
    Screen re-renders from SQLite (instant, no waiting)
        ↓
    syncService.triggerSync() runs (background)
        ↓
    Supabase upsert with client_updated_at
        ↓
    Queue marked synced
        ↓
    SyncIcon updates to ✓

  READ PATH
    Screen mounts
        ↓
    Custom hook queries SQLite
        ↓
    Renders immediately (data is always local)
        ↓
    If online: pullRemoteChanges() runs silently
        ↓
    If remote has newer rows: SQLite updated
        ↓
    Hook detects change, re-renders screen

  CONFLICT RESOLUTION
    Every local write stamps client_updated_at = now()
    Supabase upsert uses onConflict: 'id'
    Row with newer client_updated_at wins
    Works correctly for single-user personal data
    No extra logic needed

  FIRST LOGIN (initial hydration)
    After auth success:
        ↓
    syncService.initialHydration()
        ↓
    Fetch all user rows from Supabase
        ↓
    Write to SQLite with sync_status = 'synced'
        ↓
    App is fully loaded, works offline from this point

PART 10 — THE RULES (non-negotiable)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Screens never import from data/ directly.
   Screens use hooks. Hooks use repositories. Repositories use SQLite.

2. Screens never call Supabase directly.
   All remote operations go through syncService.

3. Every write goes through a repository.
   No direct SQLite inserts outside of repositories.

4. core/ has zero React Native imports.
   It must stay portable for the web app.

5. Never block the UI for a network operation.
   Write locally first, always. Show the result immediately.

6. The sync icon is the only visible sync feedback.
   No loading spinners for data that's already in SQLite.
   No toasts on sync success.
   No modals on sync failure (just icon state change).

7. Haptics have one entry point: useHaptics().
   Never call expo-haptics directly in a component.

8. All business logic lives in core/utils.ts.
   No calculation logic in components or hooks.
   Components display. Hooks fetch. Utils calculate.

PART 11 — STREAK SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A streak = any day with at least one expense OR income logged.
The mechanic is simple. The impact on daily retention is not.

CALCULATION (runs on home screen load)
  SELECT DISTINCT date(created_at) as day
  FROM expenses
  WHERE user_id = ?
  ORDER BY day DESC

  Walk backwards from today. Count consecutive days with no gap.
  Today is included even if nothing logged yet — the streak isn't
  broken until the day ends with zero entries.

DISPLAY RULE
  Only shown if streak >= 3 days.
  Position: below greeting line on home screen.
  Format: 🔥 12 days  (small, quiet — not a banner)
  At 0–2 days: hidden entirely.

RESET RULE
  If yesterday has zero entries AND today has zero entries → reset to 0.
  One missed day breaks the streak.
  This is intentional. The tension is the mechanic.

SCHEMA CHANGE NEEDED
  Add type column to expenses table:
    type TEXT NOT NULL DEFAULT 'expense'
    CHECK (type IN ('expense', 'income'))
  Streak query pulls from same table regardless of type.

FUTURE MILESTONES (not now, later)
  7 days  → quiet note in Stats section
  30 days → quiet note in Stats section
  No push notification for milestones — too aggressive.

WHY THIS WORKS
  Once a user hits day 7+, they open the app daily just to preserve
  the number. It turns weekly users into daily users without any
  push notification, without any gamification UI. Just a number.

PART 13 — GUEST MODE + ACCOUNT MIGRATION FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PHILOSOPHY
  Full functionality in guest mode. No features locked.
  No "sign up to continue" walls.
  The account exists to back up data and sync across devices.
  That's the only sell. Let the product earn the sign-up.

GUEST MODE FLOW
  1. User taps "Continue as Guest" on auth screen.
  2. guestId generated: guest_[timestamp]_[random]
     Stored in AsyncStorage key: 'haqly_guest_id'
  3. authStore.isGuest = true, authStore.guestId = guestId
  4. All SQLite writes use guestId as user_id.
  5. syncService checks for session → none → skips Supabase.
  6. Queue fills but never drains. That's fine.
  7. GuestBanner shows on home and More screens.

GUEST BANNER
  Home screen: subtle strip below greeting.
  Text: "Your data is saved on this device only."
  Action: "Back up my data →"
  More screen: prominent card at top of settings.
  Text: "Create a free account to back up and sync your data."
  Action: "Create account" button.
  Dismiss: not dismissable. It stays until they migrate.

GUEST LIMITATIONS (only these, nothing else)
  - No cloud backup
  - No multi-device sync
  - If app is deleted or device changes: data is gone
  All of this is explained clearly, not hidden.

MIGRATION FLOW (guest → account)
  Step 1: User taps "Create account" from banner.
  Step 2: Standard signup form (same auth screen, signup tab).
  Step 3: On Supabase user creation success:
    a. Real UUID received from Supabase auth.
    b. UPDATE expenses SET user_id = [real_uuid]
       WHERE user_id = [guest_id]
       — repeated for all 5 tables.
    c. UPDATE offline_queue SET payload = replace(payload, guest_id, real_uuid)
       WHERE sync_status = 'pending'
    d. All rows now have real UUID. All marked sync_status = 'pending'.
    e. triggerSync() fires → full queue drains to Supabase.
    f. AsyncStorage clears 'haqly_guest_id'.
    g. authStore.isGuest = false, guestId = null.
    h. GuestBanner disappears. SyncIcon shows ✓.
  Step 4: User is now a full authenticated user.
          Their complete history is in the cloud. Nothing lost.

EDGE CASES
  Migration fails midway: guest_id rows stay in SQLite, queue untouched.
  Retry on next triggerSync(). Idempotent — safe to run multiple times.

  User already has an account on another device:
  Login flow (not signup) + initialHydration() pulls cloud data.
  Local guest data is separate. We don't auto-merge guest + existing account.
  Show user a choice: "Keep cloud data" or "Replace with device data".

──────────────────────────────────────────────────────────
A. STREAK SYSTEM
──────────────────────────────────────────────────────────

What it is:
  Counts consecutive calendar days where at least one expense
  OR income entry was logged. Miss a full day → resets to 0.

Logic (runs in SQLite, no Supabase call needed):
  SELECT DISTINCT date(created_at) as day
  FROM expenses
  WHERE user_id = ?
  ORDER BY day DESC

  Walk the list backwards from today.
  Count consecutive days with no gap.
  If today has no entry yet — streak is still alive (day not over).
  If yesterday has no entry — streak is broken.

Storage:
  Calculated on demand from SQLite. Not stored separately.
  Fast enough — local query, no network.

Where it shows:
  Home screen, below greeting, top area.
  Format: 🔥 14 days
  Only visible when streak >= 3.
  Under 3 days — hidden. Not worth showing until it means something.

Milestone moments (subtle, not loud):
  7 days  → small glow on the streak badge, nothing else
  30 days → insight banner acknowledges it once
  No confetti. No full-screen celebration. Haqly is minimal.

Hook effect:
  Once a user hits 7+ days they will open the app daily
  just to protect the number. This is intentional.
  Same mechanic as Duolingo. Applied to financial discipline.

SQLite — no schema change needed.
  Streak is derived from existing expenses table.
  Just a query, not a stored value.

──────────────────────────────────────────────────────────
B. INCOME TRACKING + STUDENT CATEGORY
──────────────────────────────────────────────────────────

Where it lives:
  Expense screen gets a toggle at the top: Expense | Income
  Same form underneath. Only the category list changes.
  No new screen needed.

Income categories (exact, in order):
  Salary, Freelance, Business, Investment, Bonus, Student, Other

Why Student:
  A student's income is an allowance from family, a scholarship,
  or a small irregular side earning.
  "Salary" doesn't apply. "Other" feels dismissive.
  Student is honest and immediate — they see it and know it's theirs.
  No explanation needed in the UI. The word does the work.

SQLite schema change:
  Add type column to expenses table:
    type TEXT NOT NULL DEFAULT 'expense'  -- 'expense' | 'income'

  Migration: ALTER TABLE expenses ADD COLUMN type TEXT DEFAULT 'expense'
  All existing rows default to 'expense'. Safe.

Supabase schema change:
  ALTER TABLE public.expenses ADD COLUMN type TEXT DEFAULT 'expense';

How balance works:
  monthIncome  = SUM(amount) WHERE type='income'  AND month = current
  monthExpense = SUM(amount) WHERE type='expense' AND month = current
  balance      = monthIncome - monthExpense

Home screen shows:
  If income logged:
    Earned Br X   |   Spent Br Y   |   Left Br Z
    Budget ring uses income as ceiling (if no manual budget set)
    If manual budget set → manual budget takes priority

  If no income logged yet:
    Budget ring works exactly as before (manual budget only)
    No balance strip shown — don't show "Left: Br 0" when there's no data

Insight engine update (generateInsight):
  New rule: if monthExpense > monthIncome → "spending exceeds income this month"
  New rule: if monthExpense > 75% of monthIncome → surface the ratio
  New rule: if source is Student and spending is high → gentler tone

Category grid on income form:
  Same grid layout as expense categories.
  Different set of chips.
  Last selected income category persists (AsyncStorage).

Repository change — ExpenseRepository:
  getMonthIncome()    → SUM where type='income' and month=current
  getMonthExpense()   → SUM where type='expense' and month=current  (existing)
  getBalance()        → income - expense

──────────────────────────────────────────────────────────
C. GUEST MODE — FULL FUNCTIONALITY + MIGRATION TO ACCOUNT
──────────────────────────────────────────────────────────

Philosophy:
  Guest users get 100% of the product.
  No feature gates. No "sign up to continue" walls.
  The only thing guest mode doesn't have is cross-device sync.
  Account creation is framed as: "protect and back up what you've built."
  Not a gate. A reward.

How guest mode works technically:
  On "Continue as Guest" tap:
    Generate a local UUID → store in AsyncStorage as 'haqly_guest_id'
    This becomes user_id for all local SQLite writes
    Supabase is not called at all
    Sync service detects no session → skips silently
    App works identically to logged-in mode

  Everything goes to SQLite under the guest UUID.
  Expenses, checks, ledger, budget, categories — all local.
  Offline queue exists but never drains (no session to sync to).

Guest banner:
  Shows in More/Settings screen only (not home — not intrusive).
  Text: "Your data is saved on this device only."
  CTA button: "Create account to back up"
  Subtle. Not a red warning. Not a modal. Just honest.

Migration flow — when guest creates an account:
  Step 1: Guest taps "Create account to back up"
  Step 2: Standard signup form (email + password or Google)
  Step 3: Supabase creates real account → returns real user UUID
  Step 4: Migration runs:

    migrationService.migrateGuestData(guestId, realUserId)
      - SELECT all rows from SQLite where user_id = guestId
      - UPDATE each row: SET user_id = realUserId
      - Mark all as sync_status = 'pending'
      - Trigger full sync → all data uploads to Supabase
      - Clear guest UUID from AsyncStorage
      - Update authStore: isGuest = false, user = real user

  Step 5: App continues exactly where they left off.
          Streak intact. History intact. Everything intact.
          They just gained cloud sync and multi-device access.

Migration is a one-way operation.
No data is lost. No screen changes. It happens silently in the background
while the user is already looking at their home screen.

What if they skip account creation forever?
  That's fine. App works indefinitely as guest.
  If they uninstall, data is gone. That's the only cost.
  We never punish them for staying in guest mode.

authStore changes:
  isGuest: boolean
  guestId: string | null
  signInAsGuest()          → generates UUID, sets isGuest = true
  migrateGuestToAccount()  → runs migration then signs in normally

migrationService.ts (new file in services/)
  migrateGuestData(guestId, realUserId)  → as above

──────────────────────────────────────────────────────────
SYNC FLOW (background, no user action needed)
──────────────────────────────────────────────────────────

Trigger points:
  1. App comes to foreground (AppState: background → active)
  2. Network reconnects (NetInfo event: isConnected = true)
  3. Background fetch fires (every 15 min, OS-managed)
  4. User pulls to refresh on any screen

Sync process:
  syncStore.setStatus('syncing')
  SyncIcon → blue pulse
  ↓
  Check network → if offline: setStatus('offline'), stop
  ↓
  Get all pending from offline_queue ORDER BY created_at ASC
  ↓
  For each item:
    insert/update → supabase.from(table).upsert(payload, {onConflict:'id'})
    delete        → supabase.from(table).delete().eq('id', row_id)
  ↓
  Success → markSynced([ids])
  Failure → markFailed([ids]) → will retry next trigger
  ↓
  syncStore.setStatus('online')
  syncStore.lastSyncedAt = now()
  SyncIcon → hidden (idle state)

Conflict resolution:
  Every local write stamps client_updated_at = now()
  Supabase upsert: newer client_updated_at wins
  Single user app → conflicts are rare → last write wins is correct
